Getting Started: Build a Statute Ontology

Not sure where to begin? This guide walks you through building a BFO-grounded ontology of a statute in twelve steps, and shows where each step happens in the sandbox. The worked example throughout is the Texas out-of-hospital DNR ontology (TX-DNR), Health & Safety Code chapter 166.

The sandbox and the checks speed up drafting. They do not replace the three human safeguards that keep an ontology faithful to the law: the section table (step 2), the scenarios (step 7), and an independent statutory review (step 10).

Phases 1 to 3 build an ontology that passes every automated check. Step 10 tests whether it is faithful to the statute, and its findings send you back to the build.

Phase 1: Read the law

Step 1. Fix the scope and the as-of date

  • Name the chapters and subchapters. TX-DNR covers chapter 166, subchapter C (out-of-hospital orders) and subchapter E (facility orders), and nothing else.
  • Read the history note at the foot of each section. Section 166.203 was amended in 2023, adding a third route to a valid facility order; an older copy of the law has only two.
  • Never work from a bill's enrolled text alone. It shows the law as passed, not as later amended. Use it for history; use the current code for content.
In the sandbox: when you create the ontology, put the jurisdiction in Domain (e.g. Law), the code and chapter in Subject, and the scope and as-of date in Description. You can change them later on the editor's Settings tab.

Step 2. Read every section and build a section table

Read the definitions section first, then every operative section, and record each rule in a working table, one row per rule. Keep it open beside the editor the whole time: every class you add should trace to a row.

Step 3. Sort every noun into a pattern

Go down the section table and ask of each thing the law mentions what kind of thing it is. The answer picks its parent class. The Legal Ontologies Foundry patterns (LOF-ODP-001 to 004) give the legal parents; the last column shows what to pick in the sandbox's BFO Category menu.

When something fits two rows, it is usually two things. “The order” is the content (what it directs), the form (the paper), and the execution (the signing). Model all three and relate them.

In the sandbox: the menu has BFO categories only, not the Foundry patterns. Add one class per pattern first (legal content, legal document, legal act, legal role, legal position), then set each statute term's Parent Class to the matching one, so the pattern survives in the hierarchy.

Phase 2: Build

Step 4. Set up

Choose a short identifier and prefix (TX-DNR used txdnr / TXDNR) and a title that names the jurisdiction and statute. If you will publish to the Foundry, reserve an ID range and plan to import BFO 2020 and the LOF-ODP-001 to 004 base files; that setup happens outside the sandbox, in a repository edited with Protégé and ROBOT.

In the sandbox: New Ontology gives you the editor with four tabs: Classes, Properties, Individuals, and Settings.

Step 5. Write the terms

Work through the step 3 table one class at a time. On the Classes tab, click Add Class and fill in:

  • Class Name — the label: lower case, singular, unique. Add a qualifier when it would collide with an imported term (“Texas DNR order”, not “DNR order”).
  • Parent Class and BFO Category — what step 3 chose.
  • Description — a genus-and-difference definition in one sentence, in the statute's own words where you can, followed by the section it comes from and any exceptions. Quote rather than paraphrase.
  • Axioms: only what the statute fixes. An order form is a material entity that carries some out-of-hospital order; the three facility-order routes are disjoint.

Relations get the same treatment on the Properties tab: name, definition, source section, Domain, and Range.

If you used AI suggestions, revise them rather than accept them. Re-parent each suggested class to the matching pattern class from step 3; merge duplicates and split conflations (look for one class doing the work of order, form, and execution); and delete anything with no row in the section table — an extracted term the statute does not support is a claim the ontology cannot back. Avoid privation classes (“non-revoked order”), boolean expressions as class names, and propositions reified as classes.

Kinds as individuals. When legal content names a kind of thing rather than a particular one (an order directs withholding of CPR as a kind, not one episode of CPR), declare the kind as both a class and an individual. OWL 2 allows this (punning); use the Individuals tab.

Try a hard axiom first. Before committing an axiom you are unsure of, write it as first-order logic and paste it into the FOL expression tester. It reports the BFO classes and relations it recognized and lists any non-BFO terms, so a misspelled relation shows up before it reaches the ontology. For example, every out-of-hospital order form carries an order: 
forall x t (instance_of(x, OutOfHospitalDNROrderForm, t) ->
  exists y (instance_of(y, OutOfHospitalDNROrder, t) & is_carrier_of(x, y, t)))
The FOL Syntax Guide and Prover9 & CLIF guide give the accepted forms.

Step 6. Run the checks, and fix until clean

Check after every working session, not just at the end.

In the sandbox: click Export to History (or Download OWL and then Upload) to run the full analysis. The report gives, in one place, the consistency and coherence verdicts, any class placed under two BFO categories that BFO declares disjoint, an entity inventory, and a Prover9/Mace4 cross-check of the first-order translation. History keeps every run so you can compare versions.

Read the report knowing what it does and does not test:

  • The BFO check is a category-disjointness lint. It catches a class placed under both process and continuant, not a class placed under the wrong one.
  • The first-order cross-check covers subsumption and disjointness. Unless BFO background axioms are loaded, agreement confirms the class hierarchy, not existential restrictions.

For a Foundry release, also run ROBOT (reason --reasoner HermiT, the QC SPARQL checks, and report --fail-on ERROR) on the repository build. Use ROBOT as the gate that must pass and this tool as the independent check that should agree; investigate any disagreement before release.

Phase 3: Test against cases

Step 7. Write scenarios, one rule each

A scenario is a small set of hypothetical people and events that tests one rule.

  • Start from the section table. For each rule with a condition or exception, write one scenario where it applies, then change one fact to make another where it fails. TX-DNR's S1 (valid order, honored) and S2 (same, but a relative asks for CPR) differ in a single line.
  • Write the law itself once: the legislature, its power, the enactment, and the chapter as legal content, so every duty can trace back to it.
  • Build one full chain for at least one duty: grounded in the chapter, triggered by an occurrence, generated by an act realizing a role, owed to someone, with a remedy.
  • Use hypothetical names, and say so.
In the sandbox: add scenario people, documents, and events on the Individuals tab, each with its Class. Then re-run the analysis and check that the inferences you expect appear.

Step 8. Write the rules that decide

OWL alone cannot say whether responders must honor an order, because OWL assumes the world is open: it never concludes that a missing fact is false, so it can never find that no one asked for CPR. Decisions therefore go in rules that check what is recorded.

  • Write one rule per statutory condition (e.g. a SPARQL ASK query), paired with its section and a sentence saying what is the case when it fails.
  • Keep three kinds of rule apart: honoring rules decide what responders must do; validity rules decide whether an order was properly made; duty rules record obligations whose breach does not void the order. Mixing the last two was the most consequential mistake in the first TX-DNR draft.

Step 9. Read the results as a lawyer would

  • Is each verdict what the statute requires, for the reason the statute gives?
  • Does each failure message say what is the case, without double negatives? “The responders know the person to be pregnant” reads; “Not met: the responders do not know the person to be pregnant” does not.
  • Where two rules interact, is the interaction right? In TX-DNR's S5 the form appears valid, so responders must honor it, even though the order was improperly made for a minor. The result should say both, and why.

Phase 4: Check and publish

Step 10. Get an independent statutory review

The builder is the worst person to find the builder's mistakes. Give a second reader who has not seen the work the ontology (Download OWL), your rules, and one instruction: check every legal claim against the current statute, section by section.

  • If an AI drafted the ontology, the reviewer must be a person or a separate session with fresh instructions, never the one that did the drafting.
  • Ask, separately, for important rules the ontology omits entirely.
  • The reviewer must read the sections themselves, not your summary of them.
  • Spot-check before you fix: re-read the statute for any finding that would change a verdict.
  • What the review finds and you do not fix goes on a not yet modeled list, with sections.

Step 11. Document

The documentation is where a reader decides whether to trust the ontology. It should carry: scope, as-of date, and jurisdiction; a statute map (your section table with a “how it is modeled” column); the scenarios and their verdicts; what is not yet modeled; linked sources; a plain statement that it is a model, not legal advice; and a license (e.g. CC BY 4.0).

In the sandbox, the Settings tab's description is a good place for scope, as-of date, and the not-legal-advice note.

Step 12. Release

Download the OWL file and put it in a repository with checks that run on every change. Tag the first release as a pre-release (v0.1.0), submit a registry entry at draft status if you are contributing to the Legal Ontologies Foundry, and open an issue for each open question and each not-yet-modeled item.

Mistakes the review caught

The first TX-DNR draft passed every automated check and still got the law wrong in five places. The reasoner checks that the ontology is coherent, not that it is faithful to the statute; only a reader with the statute open can check that.

What the first draft didWhat the statute saysLesson
Required responders to find the order formA worn DNR identification device must be honored as the form would be (§ 166.090(b))Read the sections a rule cross-references, not only the rule itself
Treated a missing notice as making a hospital order invalidFailure to give notice “does not affect the validity” of the order (§ 166.204(b))Separate validity rules from duty rules (step 8)
Gave only the declarant the power to revokeA guardian, qualified relative, or agent may also revoke (§ 166.092(a))Model who holds a power from the statute's list, not from the obvious case
Cited one immunity section for both kinds of orderOut-of-hospital orders: § 166.094; facility orders: § 166.207, with different termsCheck each citation at the subsection level
Treated an advance directive as a directive or a medical power of attorney onlyAn out-of-hospital DNR order is also an advance directive (§ 166.002(1)(B))Reread the definitions section after modeling, not only before

Two habits prevent most of these: quote the statute's words in definitions and comments rather than paraphrasing, and keep the section table open beside the editor the whole time.

Beyond the sandbox

Everything is free. The sandbox covers drafting and checking; a full Foundry release also uses:

  • bfo-agent — drafts a first-pass ontology from a statute's text under BFO anti-pattern rules (optional; revise its output as in step 5).
  • Protégé 5 — editing classes and running the reasoner interactively (needs Java 11+).
  • ROBOT — command-line merging, reasoning, QC checks, and releases.
  • Python 3 with rdflib — running the deciding rules and a plain-language report.
  • BFO 2020 and the LOF-ODP-001 to 004 base files — the upper ontology and legal patterns every class descends from.
  • The statute, current text and history notes, from the state's official code site.
  • A second reader — a colleague, a student, or a separate agent session that has not seen your work.
